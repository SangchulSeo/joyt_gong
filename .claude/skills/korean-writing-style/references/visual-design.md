# 문서 디자인 가이드 (강조, 아이콘, 정보 위계)

문체가 좋아도 시각적으로 정돈되지 않으면 읽기 어렵다. Markdown과 HTML 출력에서 강조 요소, 아이콘, 정보 위계를 일관되게 쓰는 방법을 다룬다. 순수 텍스트(Text) 출력에는 해당 사항이 없다.

## 강조(하이라이트) 사용 원칙

강조는 절제해서 쓸 때만 효과가 있다. 한 문단에 볼드가 여러 개면 아무것도 강조되지 않은 것과 같다. 그리고 강조 수단을 고르는 것보다 먼저 해야 할 일이 있다. 바로 **무엇을 강조할지 판단하는 것**이다. 이건 사용자에게 물어볼 문제가 아니라 Claude가 내용을 읽고 스스로 판단해야 하는 부분이다.

### 무엇을 강조할지 먼저 판단한다

강조 표시를 넣기 전에 자문한다. "이 섹션을 훑어보는 독자가 가장 먼저 알고 싶어하는 게 뭔가?" 문서의 주제뿐 아니라 독자 유형(`SKILL.md`의 "독자 유형" 참고)에 따라서도 답이 다르다. 같은 비용 문서라도 개발자는 구현 난이도를, 비개발자 의사결정자는 최종 금액을 먼저 본다.

- 비용 문서라면 독자는 **얼마인지, 무료로 시작할 수 있는지**를 제일 궁금해한다.
- 장애 문서나 보안 문서라면 **심각도, 지금 뭐가 깨져 있는지**가 먼저다.
- 의사결정 문서라면 **결론과 다음 행동**이 먼저다.

이 판단 없이 "일단 단정적으로 들리는 문장에 강조를 넣는" 습관을 따르면, 실제로는 부수적인 제약 조건(예: "OO 요금제는 상업 이용 불가" 같은 경고성 문장)에 강조가 가고, 정작 독자가 찾는 숫자(가격, 무료 여부)는 다른 문장들과 똑같은 굵기로 묻혀버린다. 강조를 넣고 나서 스스로에게 "이 표시만 보고 훑어도 독자가 원하는 답이 보이는가"를 되물어 확인한다.

**단, 독자가 아직 결정을 내리지 않은 두 선택지를 나란히 비교할 때는 판단 기준이 달라진다.** "형광펜을 아예 빼서 중립을 지킨다"는 틀린 접근이다. 강조가 없으면 각 선택지의 핵심이 뭔지 안 보여서 애초에 비교가 안 된다. 진짜 필요한 건 **대칭적 강조**다. 비교하는 항목(행)마다 양쪽 선택지의 핵심 단어를 똑같은 강도로 강조한다 (예: "초기 구축" 행에서 A는 **없음**, B는 **필요**로 둘 다 볼드). 이렇게 하면 한쪽에만 힘을 싣지 않으면서도 각 항목에서 뭐가 다른지 한눈에 들어온다. 편향은 "한쪽에만 강조를 몰아줄 때" 생기지, "양쪽에 똑같이 강조를 줄 때" 생기지 않는다.

이때 레이아웃도 비교를 뒷받침해야 한다. 카드 두 개를 나란히 놓는 방식은 각 카드의 항목 개수나 길이가 다르면 높이가 안 맞고 "장점 vs 장점"을 같은 줄에서 못 보게 된다. **비교 항목이 여러 개면 카드 2개가 아니라 표를 쓴다.** 행은 비교 기준(항목), 열은 선택지(A/B)로 두면 같은 행에서 자동으로 정렬되고 양쪽을 나란히 읽을 수 있다.

선택지 이름을 붙일 때도 대칭을 지킨다. "A. 관리형 (Vercel + Supabase)" / "B. 전용 서버 (직접 운영)"처럼 한쪽은 괄호 안에 구체적 서비스명, 다른 쪽은 괄호 안에 운영 방식을 넣으면 같은 위치에 다른 종류의 정보가 들어가 헷갈린다. 괄호 안은 양쪽 다 구체적인 서비스명이나 벤더명으로 통일한다.

라벨 단어(괄호 밖) 자체도 부연 설명 없이 그것만으로 뜻이 갈라져야 한다. "관리형"은 그 자체로는 "누가 관리하는지"가 안 드러나서 반대쪽이 "관리가 필요 없다"는 뜻처럼 오해되기 쉽다. 이걸 고치겠다고 "관리형 (벤더가 운영 담당)"처럼 괄호에 설명을 욱여넣는 것도 답이 아니다 (앞서 말한 "괄호 안은 구체적 서비스명" 원칙과 충돌한다). 대신 애초에 단어 자체를 대칭적으로 고른다. 어간(공통 부분)은 같고 수식어만 반대인 단어 쌍을 쓰면 부연 설명 없이도 뜻이 갈라진다 (예: "**위탁** 운영형 (Vercel + Supabase)" vs "**직접** 운영형 (GCP, AWS 등의 VPC)"). "운영형"이라는 같은 틀에 "위탁"과 "직접"이라는 반대 수식어만 다르니, 단어만 보고도 어느 쪽이 누구 책임인지 바로 읽힌다.

HTML이라면 대칭 강조에 색까지 더할 수 있다. 그 행에서 각 선택지에게 유리한 내용이면 `--ok`(초록), 불리한 내용이면 `--danger`(빨강)로 강조색을 갈라준다. 트레이드오프 표는 "다르다"만 보여주는 게 아니라 "어느 쪽이 유리한지"까지 한눈에 읽혀야 진짜 비교가 된다. 한 항목 안에서 A에게 좋은 게 B에게는 나쁜 것일 때가 많으므로(예: 초기 구축 비용 없음=A에게 좋음, B는 구축 필요=B에게 나쁨) 보통 초록/빨강이 자연스럽게 짝을 이룬다. 다만 이건 위에서 말한 "형광펜으로 한쪽을 편애하지 않는다"는 원칙과는 다른 문제다. 색은 그 항목의 유불리를 나타내는 것이고, 강조를 어느 한쪽에만 몰아주는 것과는 다르다.

### 강조 수단은 정보의 성격에 따라 다르게 고른다

형광펜 하나로 "중요해 보이는" 문장을 다 칠하면 결국 다 같은 무게로 보여서 위계가 사라진다. 아래처럼 정보의 성격과 수단을 대응시킨다. 문서에 실제로 그 성격의 정보가 있을 때만 해당 수단을 쓴다. 다양성을 보여주려고 억지로 다 채워 넣지 않는다.

| 정보 성격 | Markdown | HTML |
|---|---|---|
| 그 섹션에서 결론적으로 가장 중요한 단 하나의 사실 (보통 숫자나 예/아니오 판단) | 볼드 | `<mark>` 배경색 하이라이트 |
| 라벨, 핵심 용어, 스캔하다 걸려야 하는 단어 | 볼드(약하게, 짧게) | `<strong>` |
| 부연 설명, 뉘앙스, 용어 최초 언급 | 이탤릭 | `<em>` |
| 파일명, 변수명, 명령어, 설정 키 같은 기술 토큰 | 인라인 코드 | `<code>` |
| 여러 줄짜리 명령어, 설정, 로그 | 코드 블록 | `<pre><code>` |
| 상태나 카테고리 라벨 (성공/경고/위험, Free/Pro) |  | 색상 텍스트나 뱃지(pill) |
| 정정, 좁은 의미의 표시 (일반 텍스트 장식으로는 거의 쓰지 않는다. 링크와 헷갈리기 쉽다) |  | `<u>` (신중하게) |

**형광펜/`<mark>`은 섹션당 한 곳 이내로 강하게 제한한다.** 여러 곳에 쓰면 "가장 중요한 것"이라는 신호력을 잃는다. 나머지 중요한 정보는 볼드나 색상 뱃지처럼 한 단계 약한 수단으로 표현해 위계를 만든다.

Markdown에는 배경색 하이라이트가 표준 문법으로 없다. `==text==` 같은 비표준 문법이나 인라인 `<mark>` HTML에 기대면 렌더러 호환성이 떨어지므로, Markdown에서 "형광펜급 강조"가 필요하면 볼드로 대체한다. 마커와 조사 사이 공백 규칙은 `common-rules.md`를 따른다.

**색상은 의미를 고정해서 쓴다.** 한번 "경고=노란색, 성공=초록색, 위험=빨간색"으로 정했으면 문서 전체에서 그 매핑을 유지한다. 같은 색을 문맥마다 다른 의미로 재사용하면 독자가 색으로 정보를 읽을 수 없게 된다. CSS 커스텀 프로퍼티(`--ok`, `--warn`, `--danger` 같은 디자인 토큰)로 정의해두고 재사용하는 방식을 권장한다.

## 정보 위계 표현

카드나 섹션 안에 성격이 다른 하위 항목(예: "현재 결정 / 필요해질 경우 / 비용 감각 / 참고")이 여러 개 있으면, 각 라벨을 `<strong>`이나 색상으로 구분하고 항목 사이에 충분한 여백을 준다. 라벨 없는 문장을 연달아 붙여 벽처럼 쌓아두지 않는다. 읽는 사람이 한눈에 "이건 어떤 종류의 정보인지" 구분할 수 있어야 한다.

나쁜 예 (라벨이 텍스트에 묻혀서 스캔이 안 됨):
```html
<p>현재 결정: Vercel(serverless) + hosted Supabase로 충분하다고 확정 VPC는 요구사항 문서에 없음</p>
<p>필요해질 수 있는 경우: 상시 워커, 장시간 배치, ...</p>
```

나은 예 (라벨을 시각적으로 분리):
```html
<dl class="decision">
  <dt>현재 결정</dt>
  <dd>Vercel(serverless) + hosted Supabase로 충분하다고 확정한다. VPC는 요구사항 문서에 없다.</dd>
  <dt>필요해질 수 있는 경우</dt>
  <dd>상시 워커, 장시간 배치, ...</dd>
</dl>
```
`<dl>`/`<dt>`/`<dd>`가 아니어도 된다. 라벨을 `<strong>` + 줄바꿈으로만 분리해도 충분하다. 핵심은 "라벨과 본문이 시각적으로 구분되는가"다.

## 장식적 레이아웃 장치는 밀도에 맞게

점선 리더(항목명 ..... 값), 큰 여백을 두는 그리드, 카드 사이 넓은 간격 같은 장치는 항목 수가 많고 스캔이 필요할 때만 효과가 있다. 항목이 두세 개뿐인데 점선이 화면 폭 전체를 가로지르거나, 카드 하나에 문장 한 줄만 들어있으면 "정돈된 느낌"이 아니라 "빈 공간이 낭비된 느낌"으로 읽힌다. 장치를 고르기 전에 실제 항목 수와 텍스트 길이를 먼저 보고, 항목이 적으면 인라인 스탯이나 촘촘한 그리드처럼 더 압축된 형태를 쓴다.

## 기술문서의 시각화 검토

기술문서를 작성하거나 수정할 때는 **각 섹션을 다이어그램, 그래프, 차트 또는 다른 시각 요소로 표현할 수 있는지 반드시 검토한다.** 시각화 결과물을 무조건 넣으라는 뜻은 아니다. 강제되는 것은 시각화 자체가 아니라 시각화 가능성에 대한 검토와 그 결과의 반영이다.

다음 정보는 시각화를 우선 검토한다.

- 구성 요소 사이의 관계와 경계
- 요청, 데이터, 상태가 이동하는 흐름
- 시간에 따른 순서와 변화
- 여러 선택지의 차이와 장단점
- 수치의 규모, 비율, 분포, 추세
- 계층, 소유 관계, 의존 관계

시각화가 텍스트나 표보다 관계와 패턴을 더 빠르고 정확하게 전달한다면 기존 설명에 추가하거나 기존 표현을 시각화로 교체한다. 이미 텍스트나 표로 충분히 명확하거나, 시각화해도 단순한 문장을 장식적으로 다시 그리는 수준이라면 넣지 않는다.

표, 다이어그램, 그래프 가운데 무엇이 적합한지도 함께 판단한다.

- 정확한 값 조회와 항목별 대조가 중심이면 표
- 구성, 흐름, 순서, 의존 관계가 중심이면 다이어그램
- 수치의 변화, 분포, 비율, 상관관계가 중심이면 그래프나 차트

Markdown에서는 목적에 맞는 Mermaid 다이어그램을 사용한다. HTML에서는 Mermaid에 의존하지 말고 HTML, CSS, SVG 또는 실제 차트 요소로 구현한다. 형식과 무관하게 시각화를 넣었다면 같은 관계나 흐름을 본문에서 다시 풀어 쓰지 않는다. 본문에는 시각화만으로 전달되지 않는 전제 조건과 예외만 남긴다.

출력 직전에 다음을 다시 점검한다.

1. 각 섹션의 시각화 가능성을 실제로 검토했는가?
2. 시각화가 더 나은 정보를 텍스트나 표로만 남겨두지 않았는가?
3. 독자의 이해를 개선하지 않는 시각화를 억지로 넣지 않았는가?
4. 시각화와 본문이 같은 내용을 중복해서 설명하지 않는가?

## 다이어그램과 아이콘 품질

- **다이어그램의 축약 수준은 독자 유형을 따른다** (`SKILL.md`의 "독자 유형" 참고). 개발자 대상이면 서비스 내부 경계(예: 하나의 백엔드 플랫폼 안에서 데이터베이스/인증/파일 저장을 별도 박스로 나누는 것)가 유용한 정보다. 비개발자나 클라이언트 대상이면 그 구분은 노이즈다. 역할 단위로 묶어서 박스 하나로 표현한다. 로컬 개발 환경, 아직 결정되지 않은 향후 검토 항목처럼 개발자에게만 의미 있는 zone도 비개발자용 다이어그램에서는 뺀다. 노드 수가 10개를 넘어가면 이미 "핵심만 보여주기"에 실패했다는 신호로 보고 통합할 방법을 먼저 찾는다.
- 노드 안팎에 잔글씨 캡션을 여러 줄 넣어 구현 세부사항을 설명하지 않는다. 그런 설명은 다이어그램이 아니라 본문 문장으로 하고, 다이어그램은 구조 자체로 읽히게 한다.
- 원, 사각형 같은 추상 도형을 조합해 임의로 만든 아이콘은 지양한다. 범례 없이는 무엇을 나타내는지 알 수 없는 도형을 다이어그램에 넣지 않는다.
- **브랜드 로고는 그 브랜드 자체를 가리킬 때만 쓴다.** "Vercel", "GitHub", "Supabase"처럼 실제로 그 서비스를 특정해서 쓰기로 확정한 경우엔 공식 로고가 맞다. 하지만 "이메일 발송", "SMS 발송"처럼 여러 업체 중 하나를 후보로만 든 **카테고리나 기능**을 나타낼 때 특정 업체(Resend, Twilio 등) 로고를 대표로 박아 넣지 않는다. 그 카드가 마치 그 업체로 확정된 것처럼 오해를 준다. 이런 경우엔 봉투(이메일), 말풍선이나 휴대폰(SMS/메시지), 종(알림) 같은 범용 아이콘을 쓴다. 이 스킬은 자주 쓰는 범용 아이콘도 `assets/icons/`에 `generic-` 접두사로 캐싱해둔다 (출처: [Heroicons](https://heroicons.com), MIT 라이선스).
- 가능하면 실제 서비스의 공식 SVG 로고를 쓴다. 이 스킬은 자주 쓰이는 브랜드 아이콘을 `assets/icons/`에 미리 캐싱해둔다 (출처: [Simple Icons](https://simpleicons.org), CC0 라이선스, 자유롭게 재사용 가능). 다이어그램을 그리기 전에 이 폴더에 필요한 아이콘이 있는지 먼저 확인하고, 없으면 Simple Icons(브랜드) 또는 Heroicons(범용 개념)에서 새로 가져와 채워 넣는다. 아이콘의 `<path>` 데이터는 반드시 실제로 받은 파일에서 그대로 복사한다. 기억에 의존해서 손으로 재구성하지 않는다. 잘못된 좌표를 만들어내면 아이콘이 깨지거나 엉뚱한 모양으로 렌더링된다. 목록은 `assets/icons/README.md`를 참고한다.
- 다이어그램 전체에서 아이콘 크기, 선 굵기, 색상 체계를 통일한다. 일부는 실사 로고, 일부는 손그림 도형을 섞어 쓰지 않는다. 브랜드 로고(채워진 실루엣)와 범용 아이콘을 같이 쓸 때도 채움 방식(solid fill)을 통일해서 아이콘 세트가 서로 다른 스타일로 튀지 않게 한다.
- **브랜드 로고는 그 브랜드 고유 색을 입힌다.** 모든 아이콘을 본문 잉크 색 하나로 통일하면 무채색으로만 보여서 브랜드를 색으로 구분할 수 없다 (Supabase는 초록, GitHub나 Vercel처럼 흑백이 공식 색인 브랜드는 무채색이 맞다. 브랜드마다 실제 공식 색을 확인하고 적용한다). 범용 아이콘(브랜드가 없는 것)은 본문 잉크색이나 강조색으로 중립적으로 둔다.
- **다이어그램 아래에 그 흐름을 다시 문장으로 풀어 설명하지 않는다.** 노드와 화살표, 역할 캡션이 이미 흐름을 전달하고 있다면 "A에서 B로 가면 C가 되고 D가 일어난다" 같은 재서술 문장은 군더더기다. 다이어그램만으로 부족한 정보(전제 조건, 예외 상황 등)가 있을 때만 짧게 보충한다.

## 표 안에서도 강조는 적용된다

표를 "데이터를 담는 그릇"으로만 보고 서식을 하나도 안 주면, 표 전체가 같은 무게로 보여서 어디를 봐야 할지 안 들어온다. 위 강조 원칙(무엇이 핵심인지 먼저 판단하고, 정보 성격에 맞는 수단을 쓰는 것)은 표 안의 셀에도 그대로 적용된다.

- 숫자나 금액 열은 단순히 정렬만 맞추지 말고, 값의 크기나 심각도에 따라 색을 입힌다 (예: 낮은 비용은 `--ok`, 큰 폭으로 뛰는 구간은 `--warn`이나 `--danger`). 이미 문서 다른 곳에서 같은 색을 같은 의미로 쓰고 있다면 표에서도 그 매핑을 그대로 따른다.
- 순서가 있는 표의 순번은 맨숫자보다 작은 배지(원형 등)로 감싸면 스캔하기 쉬워진다.
- 행 전체를 굵게 하거나 배경을 칠하는 식으로 "이 표에서 제일 중요한 행"을 표시할 수도 있다. 단, 이것도 형광펜과 마찬가지로 표 하나에 한두 곳으로 제한한다.

## 한글 줄바꿈

HTML에서 한글 텍스트에 `word-break: keep-all`을 기본으로 지정한다. 지정하지 않으면 브라우저가 한글 단어 중간이나 영문 약어와 괄호 사이("BAA(Business Associate Agreement)\n등"처럼) 같은 곳에서 임의로 줄바꿈해서, 좁은 카드나 테이블 셀에서 특히 보기 흉하게 끊긴다. `body`나 최소한 표나 카드처럼 좁은 컨테이너에는 반드시 넣는다.
