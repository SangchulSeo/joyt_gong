# 공통 규칙

문체 지시와 무관하게 항상 적용하는 규칙. 사용자 지시로 바뀌지 않는다.

## 일반 규칙

아래 4개 소제목(표기, 문장 구성, 구두점, 표현 절제) 중 지금 다루는 문제와 가장 가까운 것부터 찾아라. 전부 순서대로 읽을 필요는 없다.

### 표기

- **맞춤법**: 표준 맞춤법을 따른다.
- **띄어쓰기**: 표준 띄어쓰기 규정을 따른다.
- **외래어 표기법**: 국립국어원 외래어 표기법을 따른다. (어떤 단어를 아예 한글로 쓸지, 영어로 쓸지의 선택은 표기법이 아니라 `term-glossary.md`의 문제다. 이 항목은 일단 한글로 쓰기로 한 단어를 "올바르게" 표기하는 규칙이다.)

### 문장 구성

- **번역투 지양**: "~에 대해", "~에 있어서", 불필요한 수동태, 지시대명사 남용 같은 번역 투 표현을 피하고 자연스러운 한국어 문장으로 쓴다.
- **"다음을 따른다" 금지**: 특히 "다음을 따른다:"처럼 콜론을 붙여 목록을 여는 구성은 절대 쓰지 않는다. 목록을 열 땐 "다음과 같다."처럼 마침표로 문장을 끝내고 목록을 잇는다.
- **"와/과" vs "및"**: 완결된 문장 안에서 두 대상을 이을 땐 자연스러운 "~와/과"를 쓴다 (예: "Vercel과 Supabase로 충분히 구현 가능"). 다이어그램 노드, 표 항목, 카드 라벨처럼 문장이 아닌 압축된 짧은 표현을 이을 땐 "및"을 쓴다 (예: "상담 진행 및 일정 관리"). "및"은 딱딱해서 문장체 안에 쓰면 어색하고, "와/과"는 라벨처럼 압축된 자리에 쓰면 문장인 척하는 느낌을 준다.
- **명사만 나열하지 않기**: 개조식으로 압축하더라도 "무엇에 대한 나열인지" 최소한의 프레임(동사, 조사)은 남긴다. "상시 워커, 장시간 배치, 사설망 접근"처럼 명사만 던지면 독자가 이게 뭘 말하는지 알 수 없다. "~ 기능이 필요해지면 도입 검토"처럼 목적이나 관계를 붙인다.

### 구두점

- **가운뎃점(·)과 em dash(—) 사용 금지**: 절대 어떠한 경우에도 쓰지 않는다. 나열할 때는 다음 중 문맥에 맞는 방식을 쓴다. (단, 가운뎃점은 Text 출력에서 "A와 B" 나열 의미가 아니라 순수 장식용 구분자나 불릿 마커로 쓸 때만 예외다. 아래 "Text" 섹션을 참고한다. em dash는 이 예외에서도 제외되며 어떤 형식에서도 절대 쓰지 않는다.)
  - "A와 B" 형태의 문장
  - 쉼표로 나열
  - 불릿으로 분리
  - 절과 절을 이을 땐 마침표로 문장을 나눈다. 라벨과 값을 이을 땐 콜론을 쓴다 (아래 "콜론" 규칙 참고).
- **콜론(:)은 라벨과 값을 잇는 자리에만**: "어미:", "구두점:"처럼 짧은 명사 라벨 뒤에 값이 오는 고정 필드 자리(프리셋 항목, 이 문서의 용어 목록 등)에서만 쓴다. 완결된 문장(서술어로 끝나는 절) 뒤에 콜론을 붙여 부연 설명이나 예시를 잇지 않는다. 예: "명사구를 우선한다: "정리함"이 아니라 "정리""는 금지, "명사구를 우선한다. "정리함"이 아니라 "정리""처럼 마침표로 끊는다.
- **온점(.)**: 명사형 종결(개조식)에는 온점을 절대 찍지 않는다. 프리셋 값이나 라벨처럼 짧은 명사구로 끝나는 자리도 예외 없이 적용된다. 합니다체나 한다체 같은 서술형 문장 종결에서는 온점을 찍을지 말지가 사용자 기호에 따라 달라진다(`SKILL.md`의 "구두점" 파라미터 참고).

### 표현 절제

- **문서 안에 메타 코멘트 남기지 않기**: "이 부분은 강조 표시함", "형광펜은 핵심 사실에만 씀" 처럼 스타일이나 작성 의도를 설명하는 문장을 완성된 문서 본문에 넣지 않는다. 그런 설명은 대화로 사용자에게 전달하되, 문서 자체는 독자가 읽을 내용만 담는다. 초안을 쓰다가 스스로에게 남긴 메모가 최종 출력에 섞여 들어가지 않았는지 항상 확인한다.
- **유추 가능한 결론 덧붙이지 않기**: 독자가 앞뒤 문맥으로 스스로 유추할 수 있는 결론을 다시 문장으로 설명하지 않는다. 예를 들어 "Hobby 요금제는 상업 이용 불가"라고 쓰면 "그러니 Pro를 써야 한다"는 자명하므로 덧붙이지 않는다. 다 설명해주면 오히려 읽는 사람을 얕보는 것처럼 읽힌다.
- **핵심만 남기고 부수 정보는 생략**: 나열형 정보를 욕심내서 다 담지 않는다. 여러 세부 항목이 있으면 독자가 실제로 판단에 필요한 한두 가지로 추리고 나머지는 뺀다. 압축은 정보를 잘라내는 것이지, 문장을 뭉개서 안 읽히게 만드는 것이 아니다. 압축했는데도 여러 사실이 한 줄에 섞여 있으면 압축이 아니라 정보 손실이다. 사실 단위가 다르면 줄이나 불릿으로 나눈다.
- **얼버무리는 표현 금지**: "참고"나 "그대로"류는 전부 의심한다. "이 문서의 나머지 항목 그대로", "위 내용 참고", "(위 OO 참고)"처럼 다른 곳을 가리키며 넘어가는 표현은 실제 사실을 대신할 수 없다. 이런 표현을 쓰고 싶어지는 순간이 바로 "여기 구체적인 숫자나 사실을 계산해서 채워 넣어야 한다"는 신호다. 특히 비용이나 비교처럼 숫자가 나오는 자리에서는 "$OO 요금이 전체 비용"처럼 뭉뚱그리지 말고, 실제 조합별로 계산해서 번호를 매겨 나열한다 (예: "1) Vercel Pro + Supabase Free: $20/월", "2) Vercel Pro + Supabase Pro: $45/월"). 참고 대상이 같은 문서 안에 있어도 예외 없다. 독자가 그 자리에서 바로 답을 얻어야 한다. 출력하기 직전 "참고", "그대로", "위 내용" 같은 단어가 남아있는지 마지막으로 훑어라.
- **차트나 그래프에 쓰는 파생 수치는 원본 표와 대조해서 검증한다.** 다른 표의 값(중앙값, 합계, 범위 등)을 계산해서 그래프나 요약 카드에 쓸 때는 그 원본 표 값이 지금도 유효한지, 새로 계산한 값이 실제로 그 원본들로부터 올바르게 도출됐는지 다시 확인한다. 원본 표의 숫자가 나중에 수정되면, 그 숫자에서 파생된 다른 표, 카드, 차트의 값도 전부 연쇄적으로 다시 계산해야 한다. 그러지 않으면 눈에 잘 안 띄는 곳에 낡은 값이 계속 남는다. 이 검증은 조용히 하는 것이다. 검증했다는 사실이나 계산 과정을 문서 안에 설명으로 남기지 않는다. 그건 "얼버무리는 표현 금지" 규칙이 막는 것과 똑같은 사족이다, 결과 숫자만 정확하면 된다.

## 출력 형식별 규칙

같은 문체 지시라도 출력이 Markdown인지, HTML인지, 순수 텍스트인지에 따라 렌더링 결과가 달라진다. 문서를 작성하기 전에 어떤 형식으로 출력되는지 확인하고 아래 규칙을 적용해라.

### 섹션 간 여백

내용이 바뀌는 지점(섹션, 카드 그룹 등)에는 형식에 맞는 방식으로 충분한 간격을 준다. 여백 없이 다음 섹션이 바로 붙으면 앞 섹션이 어디서 끝났는지 눈으로 구분이 안 된다.

- **Text**: 섹션 사이에 빈 줄(엔터 두 번)을 넣는다.
- **Markdown**: heading 바로 위에 `<br />`를 삽입한다 (아래 Markdown 항목 참고).
- **HTML**: 섹션 컨테이너에 CSS `margin`이나 `gap`으로 실제 여백을 준다. 테두리선(`border-top`)만 긋고 여백을 안 주면 답답해 보인다. 구분선과 여백은 같이 간다.

### Markdown

- **볼드/이탤릭 마커와 조사 사이 공백**: 마커가 한글 조사에 바로 붙으면 마크다운 뷰어에 따라 볼드/이탤릭 처리가 깨지는 경우가 많다. 마커 뒤에 조사가 오면 띄어 쓴다.
  - `**볼드** 가` (O) / `**볼드**가` (X)
  - `*이탤릭* 이` (O) / `*이탤릭*이` (X)
  - 볼드/이탤릭을 언제, 얼마나 쓸지는 `visual-design.md`의 강조 사용 원칙을 따른다.
- **숫자 범위에 물결표(~) 사용 금지, 하이픈으로 통일**: `12~30, 35~40`처럼 여러 범위를 나열하면, 줄바꿈 등의 이유로 `~30, 35~` 형태로 걸쳐 보일 때 일부 렌더러가 이를 취소선(~~text~~)으로 오인식한다. 물결표 대신 항상 하이픈을 쓴다. (`12-30`)
- **heading 앞 여백**: `#`, `##`, `###`, `####` 헤딩 바로 위에 `<br />`를 삽입해 렌더러에서 헤딩 위쪽 여백이 부족한 문제를 보완한다.
- **기술문서의 시각화**: 각 섹션의 시각화 가능성을 반드시 검토한다. 아키텍처, 설계, 흐름을 Mermaid 다이어그램으로 표현했을 때 텍스트보다 독자가 이해하기 좋다면 추가하거나 기존 설명을 교체한다. 시각화가 이해를 개선하지 않으면 넣지 않는다. 자세한 판단 기준은 `visual-design.md`의 "기술문서의 시각화 검토"를 따른다.
- 나열 시 가운뎃점 금지 규칙은 Markdown에서도 동일하게 적용된다 (위 일반 규칙 참고).
- **이모지**: 쓸지 말지는 사용자 기호에 따라 달라진다. 기본값은 쓰지 않는 쪽이다.

### HTML

- **기술문서의 시각화**: 각 섹션의 시각화 가능성을 반드시 검토한다. 실제 그래프나 차트, 다이어그램이 표나 텍스트보다 독자가 이해하기 좋다면 추가하거나 기존 설명을 교체한다. Mermaid 대신 HTML, CSS, SVG 또는 실제 차트 요소로 직접 구현한다. 시각화가 이해를 개선하지 않으면 넣지 않는다. 자세한 판단 기준은 `visual-design.md`의 "기술문서의 시각화 검토"를 따른다.
- **강조, 정보 위계, 아이콘과 다이어그램 품질**: `visual-design.md`를 반드시 참고한다. HTML은 강조 수단(볼드/이탤릭/하이라이트/색상뱃지)이 많아서 절제하지 않으면 오히려 가독성을 해친다.
- **이모지 사용 금지, 예외 없음**: 아이콘이 필요한 자리에는 이모지 대신 항상 SVG 아이콘을 쓴다. 사용자가 이모지를 요청해도 HTML 출력에서는 적용하지 않는다. SVG 아이콘 확보 방법은 `visual-design.md`의 "다이어그램과 아이콘 품질"을 따른다.

### Text (순수 텍스트)

- 마크다운 문법(`**`, `#`, `` ` `` 등)을 그대로 노출하지 않는다. 강조나 구조가 필요하면 텍스트로 표현 가능한 방식(줄바꿈, 들여쓰기, 번호 매기기)을 쓴다.
- **이모지**: 다른 형식보다 레이아웃으로 정보를 꾸밀 수단이 제한적이므로, 강조나 구분이 필요할 때 제한적으로 쓸 수 있다. 남용하지 않는다.
- **가운뎃점(·)은 장식용 구분자나 불릿 마커로 예외적으로 허용**: 마크다운 목록이나 HTML `<li>` 같은 실제 목록 문법이 없는 Text에서는, "A와 B"라는 나열 의미 없이 순수하게 항목을 구분하는 시각적 기호로 가운뎃점을 쓸 수 있다.
  - 인라인 구분자: `React.js · Vite · TypeScript · CSS Modules`
  - 들여쓰기 불릿 마커: 전각 공백(`　`)으로 들여쓴 뒤 `· `로 항목을 시작 (`　· 항목 내용`)
  - 이 예외는 Text에서만 적용된다. Markdown과 HTML에서는 위 일반 규칙대로 가운뎃점을 절대 쓰지 않는다.
- **em dash(—)는 Text에서도 예외 없이 금지**: 라벨과 부연 설명을 잇고 싶을 때는 콜론(:)이나 하이픈(-)을 쓴다.
