# 한국어 문체 적응형 스킬

## 철학

문체는 "기술문서용", "자기소개서용" 같은 문서 종류별 프리셋으로 미리 다 정의할 수 없다. 어미, 구두점, 문장 밀도 같은 요소들은 문서 종류와 무관하게 독립적으로 조합되고, 한 문서 안에서도 부분마다(본문 vs 불릿) 다르게 섞인다. 그래서 이 스킬은 두 층으로 동작한다.

1. **공통 규칙**: 거의 불변이다. 맞춤법, 띄어쓰기, 외래어 표기법처럼 처음부터 고정해도 안전한 규칙이다. 자세한 내용은 `references/common-rules.md`를 참고한다.
2. **개인 프리셋**: 비어있는 상태로 시작해 사용하면서 채워지는, 사용자가 실제로 반복 지시한 파라미터 조합이다. 자세한 내용은 `presets/presets.md`를 참고한다.

미리 다 만들어두지 않는다. 실제로 반복되는 조합만 쌓는 구조가 핵심이다.

## 항상 적용: 공통 규칙

문체 지시와 무관하게 아래는 항상 지킨다. 자세한 항목과 근거는 `references/common-rules.md`를 읽어라.

- 맞춤법, 띄어쓰기, 외래어 표기법
- 번역투 지양
- 가운뎃점(·)과 em dash(—) 사용 금지: 나열할 땐 "A와 B" 문장, 쉼표, 또는 불릿으로 분리
- 출력 형식(Markdown/HTML/Text)에 따른 렌더링 규칙 (볼드체 공백, 숫자 범위 표기, heading 앞 여백 등)

용어를 한글로 쓸지 영어로 쓸지 판단할 땐 `references/term-glossary.md`의 패턴을 따른다.

## 동작 흐름

### 0. 대상이 코드베이스 전체의 함수/변수/주석 설명인 경우

"프로젝트 전체 주석 문체 통일해줘", "함수 설명 정리해줘"처럼 대상이 개별 문서가 아니라 코드베이스에 흩어진 한국어 설명(JSDoc, docstring, 인라인 주석, 커밋 메시지 등)일 때는 아래 1번 문서 흐름과 다르게 동작한다.

- **독자 유형 질문 생략**: 코드 주석의 독자는 사실상 항상 "이 코드를 유지보수하는 개발자"다. 문서처럼 매번 되묻지 않고 개발자 대상으로 바로 진행한다.
- **어미는 기존 관습 우선**: 코드 주석은 합니다체/해요체보다 명사형 종결(개조식)이나 평서형이 흔하다. 먼저 grep 등으로 프로젝트에 이미 쓰인 주석 스타일을 파악하고, 그 관습을 유지한 채 다듬는다. 관습이 파일마다 뒤섞여 있으면 어떤 스타일로 통일할지 사용자에게 되묻는다.
- **공통 규칙은 문서와 동일하게 적용**: 맞춤법, 띄어쓰기, 외래어 표기법, 번역투 지양, 가운뎃점 금지는 코드 주석에도 그대로 적용한다.
- **범위는 파일 단위가 아니라 프로젝트 전체**: 요청받은 파일 하나만 보고 끝내지 말고, 같은 종류의 설명(예: 모든 함수 docstring)이 프로젝트 전역에 얼마나 더 있는지 확인한 뒤 일관되게 반영한다.
- 프리셋 저장/불러오기(아래 3-6번)는 코드 주석에도 동일하게 적용된다. 반복되는 주석 스타일 조합을 프리셋으로 쌓을 수 있다.

### 1. 문서 작성/개선 요청: 독자 유형부터 확인

새 문서를 쓰거나 기존 문서를 개선해달라는 요청을 받으면, 다른 무엇보다 먼저 **독자가 누구인지** 확인한다 (개발자 / 비개발자 / 면접관과 과제 검토관 같은 평가자 / 이해관계자 등). 프리셋을 불러오는 경우에도 마찬가지다. 프리셋은 어미와 구두점 같은 문체 파라미터의 조합이지 독자 유형을 담고 있지 않으므로, 같은 프리셋이라도 독자가 다르면 다시 확인한다.

독자 유형은 이후 판단의 전제가 된다. 구체적으로는 다음과 같다.
- **격식/존댓말 여부**: 면접관, 과제 검토관/채점자처럼 나를 평가하는 독자에게는 반말이나 지나치게 캐주얼한 개조식보다 합니다체 같은 격식체가 사실상 기본값에 가깝다. 독자 유형을 확인하는 순간 이미 어미 후보가 좁혀진다는 뜻이다. 평가자 대상인데 반말이나 극단적 개조식을 기본으로 제안하지 않는다.
- **용어 선택** (`term-glossary.md`): 비개발자와 평가자 대상이면 약자를 더 적극적으로 풀어쓰고, 개발자 대상이면 통용 약자는 생략할 수 있다.
- **강조 우선순위** (`visual-design.md`): "독자가 가장 궁금해하는 것"이 독자 유형에 따라 달라진다. 평가자는 성과/결론, 비개발자 이해관계자는 비용/일정/리스크, 개발자는 기술적 근거를 먼저 찾는다.
- **문장 밀도와 전문성 수준**: 같은 사실이라도 독자에 따라 설명을 더 풀거나 더 압축한다.

독자 유형을 확인했으면, 이어서 나머지 문체도 구체적으로 되묻는다. 이때 완전히 백지 상태로 묻지 말고, 독자 유형에서 자연스럽게 좁혀지는 후보를 먼저 제안한다 (예: "평가자 대상이시니 합니다체가 기본일 것 같은데, 맞을까요?"). 구체적으로는 다음과 같다.
- 어미는 어떻게 할지 (합니다체 / 해요체 / 반말 / 개조식)
- 서술형 문장으로 쓸지, 개조식으로 나열할지
- 본문과 불릿/목록에 다른 문체를 쓸 부분이 있는지
- `presets/presets.md`에 저장된 프리셋이 있다면, 그중 하나를 쓸지도 함께 물어본다

문서가 기술문서 성격이면(설계 문서, 아키텍처 설명 등) 사용자에게 시각화 포함 여부를 선택하게 넘기지 말고, **Claude가 각 섹션의 시각화 가능성을 반드시 검토한다.** 관계, 흐름, 순서, 비교, 규모, 추세를 다이어그램이나 그래프, 차트로 표현했을 때 독자가 텍스트나 표보다 더 빠르고 정확하게 이해할 수 있다면 시각화를 추가하거나 기존 표현을 시각화로 교체한다. 시각화가 이해를 실질적으로 개선하지 않으면 넣지 않는다. 구체적인 판단 기준과 출력 형식별 구현 방식은 `references/visual-design.md`의 "기술문서의 시각화 검토"를 따른다.

### 2. 그 자리에서 지시 반영

"가운뎃점 빼줘", "불릿은 명사형으로 끝내줘" 같은 지시는 즉시 그 자리에서만 반영한다. 별도 요청이 없으면 저장하지 않는다.

### 3. 프리셋 저장: 명시적 요청 시에만

사용자가 "이거 저장해줘", "이 조합 OO으로 저장해줘"라고 **명시적으로** 말할 때만 `presets/presets.md`에 항목을 추가한다. 자동 저장하거나 매번 저장할지 제안하지 않는다.

- 이름은 지금까지의 파라미터 조합을 보고 Claude가 제안하고, 사용자가 확정하거나 바꾼 이름을 사용한다.
- 프리셋은 문서 종류가 아니라 파라미터 조합으로 정의한다 (`presets/presets.md`의 형식을 따를 것).

### 4. 프리셋 불러오기: 명시적 호출만

사용자가 "OO 프리셋으로 써줘"처럼 **이름을 직접 말했을 때만** 해당 프리셋을 불러와 적용한다. 프리셋이 여러 개 쌓여도 이름을 말하지 않은 상태에서 문맥만 보고 자동으로 특정 프리셋을 골라 적용하지 않는다. 대신 위 1번 흐름대로 되묻는다.

### 5. 기존 프리셋과 겹치지만 다른 요청

"블로그 프리셋인데 이번엔 느낌표 허용해줘"처럼 기존 프리셋 기반이지만 일부만 다른 요청이 오면, 기존 프리셋을 덮어쓰지 않고 그 요청에서만 일시 적용한다. 저장할지는 다시 물어본다.

### 6. 프리셋 수정 및 삭제

"OO 프리셋 삭제해줘", "OO 프리셋에 느낌표 허용 추가해줘"처럼 **명시적 커맨드**가 있을 때만 `presets/presets.md`를 수정한다. 다른 지시를 하다가 넌지시 유추해서 기존 프리셋을 바꾸지 않는다.

### 7. 출력 직전 자기 점검

시각 디자인, 다이어그램, 아이콘처럼 눈에 보이는 부분에 집중하다 보면 온점 생략이나 가운뎃점 금지 같은, 눈에 잘 안 띄지만 기계적으로 지켜야 하는 규칙을 놓치기 쉽다. 문서를 완성했다고 내놓기 전에 지금 적용 중인 공통 규칙과 프리셋(특히 구두점 규칙)을 기준으로 한 번 더 훑어라. 별도 텍스트를 새로 작성할 때뿐 아니라, 예시나 목업처럼 부수적으로 쓰는 한국어 문구에도 똑같이 적용된다.

기술문서라면 최종 출력 전에 시각화 검토를 실제로 수행했는지 다시 확인한다. 시각화 결과물이 반드시 있어야 한다는 뜻은 아니다. 시각화가 더 나은 섹션을 텍스트나 표로만 남겨두지 않았는지, 반대로 이해를 개선하지 않는 장식용 시각화를 억지로 넣지 않았는지를 점검한다. 시각화를 추가하거나 교체했다면 같은 내용을 본문에서 불필요하게 반복하지 않았는지도 확인한다.

문서에 "정리", "요약" 같은 결론 섹션이 있다면 문서를 수정할 때마다 반드시 그 섹션도 다시 검토한다. 요약은 본문이 바뀌어도 그대로 남아있기 쉬운 부분이라 가장 먼저 낡은 정보가 된다. 최종 출력 직전에 "이 요약이 지금 본문 전체의 맥락을 함축하고 있는가"를 확인하고, 본문에서 빠지거나 바뀐 내용이 요약에 그대로 남아있지 않은지 점검한다.

## 독자 유형 (문체 파라미터 이전에 확인)

문체 파라미터가 "어떻게 쓸지"라면, 독자 유형은 "누구에게 쓸지"다. 프리셋에는 포함하지 않는다. 같은 문체 프리셋도 다른 독자에게 재사용될 수 있기 때문이다. 매번 문서를 시작할 때 확인한다 (위 동작 흐름 1번 참고).

- 개발자
- 비개발자 (이해관계자, 동료, 고객 등)
- 평가자 (면접관, 과제 검토관/채점자)
- 불특정 다수 (블로그 글처럼 누가 읽을지 특정할 수 없는 공개 대상): 특정 배경지식을 가정할 수 없으므로 전문용어는 더 쉽게 풀어 쓰고, 격식은 평가자만큼 딱딱할 필요는 없지만 문서 성격에 따라 사용자와 함께 정한다
- 그 외 사용자가 지정하는 유형

## 문체를 구성하는 파라미터

아래는 지금까지 확인된 파라미터다. 고정 목록이 아니다. 실제로 반복 등장하는 파라미터만 프리셋에 반영하고, 쓰지 않는 파라미터를 미리 정의하지 않는다.

- **어미**: 합니다체 / 해요체 / 반말 / 명사형 종결(개조식)
- **구두점**: 느낌표/물음표 허용 여부
  - 온점은 명사형 종결(개조식)에 절대 찍지 않고, 합니다체/해요체/한다체 같은 서술형 종결에서만 찍을지 말지가 사용자 기호에 따라 달라진다(`references/common-rules.md`의 "온점" 규칙 참고).
- **부분별 혼용**: 본문과 불릿/목록에 서로 다른 어미와 종결 적용 여부
- **문장 밀도**: 서술형 문장 vs 개조식 나열
- **어휘**: 전문용어 영문 병기 여부, 번역투 표현 제거 여부
